## 🔵 Phase 1 — Clarify (plain language): Intent (feature) or Problem (fix)

- **Prose quality (same model pass):** Reuse the run-loaded `workflow-prose-quality.md` contract and apply it before output. Read it now only if this is the first decision-bearing artifact or a fresh-context/digest change invalidated the loaded copy; add no agent, call, step, or gate.

Goal: source-backed product intent for features and a usable problem brief for fixes BEFORE research/plan. The user owns WHAT/WHY: goal, actor, visible behavior, boundaries, success, and material product/policy consequences. The agent owns HOW: architecture, dependencies, data model, internal APIs, code structure, tests, migrations, performance/concurrency mechanism, and implementation order. Never ask the user to design the solution. → reference.md "Intent clarification" / "Fix mode".

- **Codex planning context boundary (large `full|plan`).** After `status` proves the final Contract-4 action `confirmed`, hand the remaining Phase-1 intent lock through the clean Phase-4 build decision to exactly one fresh `top` planning worker with `fork_turns="none"`; this replaces the parent planner, it is not an extra opinion. Pass the literal workspace/plugin/run paths, the Active-Run owner host/session from that status, `INTAKE.md`, `INTAKE-2.md`, `RESEARCH.md`, and the exact phase/gate command contract. Every delegated Active-Run write sets `KIMIFLOW_SESSION_HOST=codex` and `KIMIFLOW_SESSION_ID=<owner>`; after confirmation the item command is exactly `active-run.sh append-item --title "<title>" --kind feature --write` with no run argument. The worker may create the required Intent Critic and review seats, but returns no progress messages. The parent does not reread or duplicate Phase 1–4: call one `wait` with `timeout_ms=3600000`, and repeat only if a required child completion wakes it before the planning worker is terminal—never poll every 30 seconds. Accept only `READY_PHASE5` with plan digest/review verdict or `NEEDS_DECISION` with the run-local artifact. A missing worker route uses the current-context fallback. Small/quick and pre-confirmation user discussion remain in the parent.

- **Codex intake command economy (same evidence, fewer turns).** Before `scope_ready`, use the already loaded request/project brief plus one prose-quality read; do not inventory or read product code/tests. After `scope_ready`, derive the smallest plausible affected-path set from the selected contract, list tracked paths at most once, update STATE, and create the codebase basis before reading product bytes. Then make one consolidated bounded read of only existing affected files, their directly matching existing tests, and named project instructions; never use broad `rg --files`, wildcard every test, or guess a test filename and retry after it is missing. A required wider inspection is one deliberate expansion from evidence, not repeated discovery. Coalesce independent read-only helpers in one host call where their contracts permit it. These limits reduce orchestration calls only: provenance coverage, current bytes, counter-perspective, research, and both user checkpoints remain unchanged.

- **Coverage scan first:** before `scope_ready`, inspect the request and already supplied project brief; after it, inspect the bounded code, project docs, tests, memory, and current sources selected above. Mark each product dimension with `user_explicit|user_confirmed|project_evidence|reversible_default|not_applicable|unknown_material`; goal, behavior, and success require user/evidence provenance, never a default. Translate a necessary technical-looking uncertainty into its product consequence (for example "must it work offline?", never "which database?").
- **Mandatory Product Intake for fresh Contract 4:** use STATE `Interaction language` for every visible question and label; never redetect or translate later. Start the scope draft with exactly `<!-- kimiflow:intake contract=4 schema=2 stage=scope round=1 confirmation=scope_deliberation user_language=<STATE tag> -->`. Every field is one literal `Name: value` line, never a Markdown heading: exactly one `Problem:`, `Observable success:`, `Boundary:`, `Included:`, `Later:`, `Excluded:`, `Counter perspective:`, `Completeness check:`, `Action scope_ready:`, and `Action discuss:`, plus 2–5 ordered distinct `Option N:` lines. Options may recommend adjacent functions, trade-offs, or a smaller solution, but may not silently expand scope. Register that exact file with `active-run.sh await-user --run .kimiflow/<slug> --kind intake --round 1 --request .kimiflow/<slug>/INTAKE.md --reason scope_deliberation --write`, then present its localized `scope_ready` and `discuss` actions. The user must explicitly choose one; generic assent, defaults, cancellation, timeout, or auto-resolution do not count. This is a discussion checkpoint, not a product-contract confirmation: label `scope_ready` as continuing/finalizing the draft and never as confirm/approve/accept/adopt. This remains true for an existing prepared run.
- **Pi/FirstMate boundary:** the invoking Pi session is only Captain and owns every user discussion and confirmation; it starts Main from immutable launch input and never runs this phase itself. Visible Kimiflow Main owns Phase 1, may use its own ordinary FirstMate Scouts for bounded `stage=research` evidence, and routes one concise `needs-decision` artifact through FirstMate status to Captain. Captain discusses it and replies through `kimiflow_crew send`. Ships and confirmed review Scouts remain closed until the final contract and self-contained brief exist. A confirmed child does not create another Active Run, replay Phase 1, manufacture intake receipts, or talk to the user. Missing Main/Crew support is an explicit fallback, never a simulated hierarchy.
- **Intent Critic:** after final confirmation and before writing `INTENT.md`, `large`/critical features visibly run exactly one independent fresh-context critic over the request + compact confirmed contract (≤900 input words, output only `COVERAGE_OK` or ≤5 missing user-owned facts; no HOW). Include every confirmed `Requirement Rn` verbatim before shortening descriptive fields. On Codex use one `fork_turns="none"` worker. Local judgment may never write `critic=passed`; record it only from `COVERAGE_OK`. A fact truly absent from the confirmed contract returns to the existing `corrected` action; if the critic merely missed a verbatim requirement, point the same critic to that row once instead of creating another worker or user round. Never create a third intake stage. Small runs may fold the identical check locally and record `critic=folded`. A missing fresh-worker route uses the existing fallback without a new user round.
- **Discuss, research, then confirm exactly once:** `discuss` records no receipt and replaces the current scope draft after conversation. `scope_ready` writes the stage-bound content-free discussion receipt; **stay in Phase 1 and do not call `phase-read --phase 2` yet**. Determine the affected paths, update STATE, run exactly `hooks/codebase-basis.sh create --run .kimiflow/<slug> --write`, and copy its complete `scope_research_marker` output as the first line of `RESEARCH.md`; do not calculate or reconstruct either digest. Perform only Phase 2's bounded current-codebase/research comparison without expanding the selected scope and record `Scope result: non_expanded`. Start `INTAKE-2.md` with exactly `<!-- kimiflow:intake contract=4 schema=2 stage=final round=2 confirmation=final_contract cause=scope_ready user_language=<STATE tag> -->`. Again use only literal `Name: value` lines: exactly one `Problem:`, `Roles and boundaries:`, `Included:`, `Excluded:`, `Observable success:`, `End-to-end example:`, `Action confirmed:`, and `Action corrected:`, plus 2–7 ordered distinct `Step N:` and 1–20 ordered `Requirement Rn:` lines. Register it with `active-run.sh await-user --run .kimiflow/<slug> --kind intake --round 2 --request .kimiflow/<slug>/INTAKE-2.md --reason final_contract --write`, then present its localized `confirmed` and `corrected` actions. The user must explicitly choose one. `corrected` records no receipt and replaces the unconfirmed final draft; only `confirmed` is an approval and locks intent. Build `INTENT.md` with `question_rounds=2` and copy every final field, `Step N`, and `Requirement Rn` byte-equivalently, but **omit both `Action confirmed:` and `Action corrected:` rows**; they authorize the receipt and are not product intent. Technical HOW remains agent-owned. Phase 2 entry is mechanically refused until `clarify-gate.sh --record-intent-lock` has opened and pinned the confirmed lock.

- **Feature → intent clarification:** perform the provenance scan, run the two explicit stages above, write `INTENT.md` from the confirmed final draft, and show the same simple flow. A route that will actually build needs current implementation authority; `plan`/`grill` stays no-code and never asks for future build permission.
- **Fix → working problem brief:** capture symptom, expected vs. actual, and available reproduction context in `PROBLEM.md`; inspect and diagnose immediately when sufficient. No routine Human Gate here. After the cause is proven, only a material product/authority/risk decision may pause before the bounded fix.
- **Audit → scope clarification:** capture paths, aggression, behavior-preserve constraints, do-NOT-touch hints, and what stays untouched → write `AUDIT-INTENT.md`. Discovery stays read-only and requests no cleanup authority; only a later user-selected fix slice may authorize implementation.
- **Mechanical clarify gate:** after the final confirmation, run `${CLAUDE_PLUGIN_ROOT:-$CLAUDE_SKILL_DIR}/hooks/clarify-gate.sh .kimiflow/<slug> --record-intent-lock` (Codex: `KIMIFLOW_HOST=codex` and `KIMIFLOW_PLUGIN_ROOT`). `OPEN` is required. Schema-2 Contract 4 validates both exact stage grammars, matching language/action/contract digests, current `CODEBASE-BASIS.json`, non-expanded research scope, final-contract equality with `INTENT.md`, ordered requirements, and the one-shot Active-Run-pinned lock. Existing Contract-4 schema 1, Contract 3, audits, fixes, trivial, and older runs retain their compatible contracts.
- **Mechanical adaptive classification (schema 5, non-trivial):** after confirmed Intent/Problem, rerun `hooks/adaptive-control.sh classify --run .kimiflow/<slug> --write`. If `product_decision_open=true`, return to this same intake boundary; never synthesize its answer. If its scope is higher than the active scope, run `hooks/active-run.sh rescope --run .kimiflow/<slug> --classification .kimiflow/<slug>/ADAPTIVE-CLASSIFICATION.json --write`; downgrade is forbidden. Copy only the receipt's exact `Domain complexity: off|active` and `Operational impact: off|active` selectors into STATE. The classifier is local, bounded, deterministic and adds no user gate.
