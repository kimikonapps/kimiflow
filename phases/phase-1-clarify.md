## 🔵 Phase 1 — Clarify (plain language): Intent (feature) or Problem (fix)

Goal: source-backed product intent for features and a usable problem brief for fixes BEFORE research/plan. The user owns WHAT/WHY: goal, actor, visible behavior, boundaries, success, and material product/policy consequences. The agent owns HOW: architecture, dependencies, data model, internal APIs, code structure, tests, migrations, performance/concurrency mechanism, and implementation order. Never ask the user to design the solution. → reference.md "Intent clarification" / "Fix mode".

- **Coverage scan first:** inspect the request, code, project docs, tests, memory, and current sources. Mark each product dimension with `user_explicit|user_confirmed|project_evidence|reversible_default|not_applicable|unknown_material`; goal, behavior, and success require user/evidence provenance, never a default. Translate a necessary technical-looking uncertainty into its product consequence (for example "must it work offline?", never "which database?").
- **Mandatory Product Intake for fresh Contract 4:** use STATE `Interaction language` for every visible question and label; never redetect or translate later. First write one schema-2 scope draft containing exactly `Problem`, `Observable success`, `Boundary`, 2–5 ordered compatible `Option N` suggestions, `Included`, `Later`, `Excluded`, one honest `Counter perspective`, and one `Completeness check`. Options may recommend adjacent functions, trade-offs, or a smaller solution, but may not silently expand scope. The user must explicitly choose the localized `scope_ready` or `discuss` action; generic assent, defaults, cancellation, timeout, or auto-resolution do not count. This is a discussion checkpoint, not a product-contract confirmation: label `scope_ready` as continuing/finalizing the draft and never as confirm/approve/accept/adopt. This remains true for an existing prepared run.
- **Pi Captain boundary:** in a Pi Worker, persist `await-user` and end the turn immediately. Never call `request_user_input`/`AskUserQuestion`, print a second Worker question, or wait for direct Worker input. The Runner publishes the durable draft and localized actions in the Captain; only the Captain reply resumes this exact Worker session.
- **Intent Critic:** for `large`/critical features, run one bounded fresh-context critic over the request + compact coverage draft (≤900 input words, output only `COVERAGE_OK` or ≤5 missing user-owned facts; no HOW). On Pi, call `kimiflow_subagent` with `role=intent_critic`, `round=1`, and `seat=intent-critic-1`; it is a visible read-only Herdr/Pi worker and may run before the final contract. Record `critic=passed`. `small|quick` folds the scan into the top orchestrator and records `critic=folded`; only a genuinely unavailable subagent tool permits the top-orchestrator fallback on a large run.
- **Discuss, research, then confirm exactly once:** `discuss` records no receipt and replaces the current scope draft after conversation. `scope_ready` writes the stage-bound content-free discussion receipt; while Phase 1 remains open, run Phase 2's bounded current-codebase/research comparison without expanding the selected scope. Return with one schema-2 final draft containing exactly `Problem`, 2–7 ordered `Step N`, `Roles and boundaries`, `Included`, `Excluded`, `Observable success`, one `End-to-end example`, and ordered `Requirement Rn`. The user must explicitly choose the localized `confirmed` or `corrected` action. `corrected` records no receipt and replaces the unconfirmed final draft; only `confirmed` is an approval and locks intent. Technical HOW remains agent-owned.

- **Feature → intent clarification:** perform the provenance scan, run the two explicit stages above, write `INTENT.md` from the confirmed final draft, and show the same simple flow. A route that will actually build needs current implementation authority; `plan`/`grill` stays no-code and never asks for future build permission.
- **Fix → working problem brief:** capture symptom, expected vs. actual, and available reproduction context in `PROBLEM.md`; inspect and diagnose immediately when sufficient. No routine Human Gate here. After the cause is proven, only a material product/authority/risk decision may pause before the bounded fix.
- **Audit → scope clarification:** capture paths, aggression, behavior-preserve constraints, do-NOT-touch hints, and what stays untouched → write `AUDIT-INTENT.md`. Discovery stays read-only and requests no cleanup authority; only a later user-selected fix slice may authorize implementation.
- **Mechanical clarify gate:** after the final confirmation, run `${CLAUDE_PLUGIN_ROOT:-$CLAUDE_SKILL_DIR}/hooks/clarify-gate.sh .kimiflow/<slug> --record-intent-lock` (Codex: `KIMIFLOW_HOST=codex` and `KIMIFLOW_PLUGIN_ROOT`). `OPEN` is required. Schema-2 Contract 4 validates both exact stage grammars, matching language/action/contract digests, current `CODEBASE-BASIS.json`, non-expanded research scope, final-contract equality with `INTENT.md`, ordered requirements, and the one-shot Active-Run-pinned lock. Existing Contract-4 schema 1, Contract 3, audits, fixes, trivial, and older runs retain their compatible contracts.
- **Mechanical adaptive classification (schema 5, non-trivial):** after confirmed Intent/Problem, rerun `hooks/adaptive-control.sh classify --run .kimiflow/<slug> --write`. If `product_decision_open=true`, return to this same intake boundary; never synthesize its answer. If its scope is higher than the active scope, run `hooks/active-run.sh rescope --run .kimiflow/<slug> --classification .kimiflow/<slug>/ADAPTIVE-CLASSIFICATION.json --write`; downgrade is forbidden. Copy only the receipt's exact `Domain complexity: off|active` and `Operational impact: off|active` selectors into STATE. The classifier is local, bounded, deterministic and adds no user gate.
