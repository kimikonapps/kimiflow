## 🔵 Phase 1 — Clarify (plain language): Intent (feature) or Problem (fix)

- **Prose quality (same model pass):** Reuse the run-loaded `workflow-prose-quality.md` contract and apply it before output. Read it now only if this is the first decision-bearing artifact or a fresh-context/digest change invalidated the loaded copy; add no agent, call, step, or gate.

Goal: source-backed product intent for features and a usable problem brief for fixes BEFORE research/plan. The user owns WHAT/WHY: goal, actor, visible behavior, boundaries, success, and material product/policy consequences. The agent owns HOW: architecture, dependencies, data model, internal APIs, code structure, tests, migrations, performance/concurrency mechanism, and implementation order. Never ask the user to design the solution. → reference.md "Intent clarification" / "Fix mode".

- **Codex planning context boundary (large `full|plan`).** Once the coverage scan has no material unknown, one fresh `top` planning worker with `fork_turns="none"` may own Phases 2–3 and return `READY_FOR_CONFIRMATION` with the PLAN digest and compact product contract. It receives literal workspace/plugin/run paths and writes only run-local planning artifacts. The parent asks the single Phase-4 confirmation and does not replay the planning work. Small/quick stays in the parent.

- **Codex intake command economy.** Use the supplied request/project brief first, derive the smallest plausible affected-path set, list tracked paths at most once, then make one consolidated bounded read of the affected files, matching tests, and named instructions. Expand once only when evidence requires it. This reduces calls, not current-HEAD evidence or plan quality.

- **Coverage scan first:** inspect the current request, supplied project brief, and bounded current project evidence. Mark each product dimension with `user_explicit|project_evidence|reversible_default|not_applicable|unknown_material`; goal, behavior, and success require user/evidence provenance, never a default. Ask one compact batch only when `unknown_material` would change visible behavior, scope, policy, or acceptance. Translate a technical-looking uncertainty into its product consequence (for example "must it work offline?", never "which database?"). When coverage is complete, continue without a confirmation or scope-ready action.
- **Provisional intent for fresh Contract 4:** write `INTENT.md` from the current request and any resolved answers before Phase 2. It is the product WHAT/WHY input to research and planning, not yet an authorization receipt. Preserve the opening request's `Interaction language`; keep `unknown_material=0`, technical HOW agent-owned, and `question_rounds=1` for the one final Phase-4 confirmation. Existing active schema-2/two-stage runs continue their pinned `scope_ready|discuss` then `confirmed|corrected` lifecycle without migration.
- **Pi/FirstMate boundary:** the invoking Pi session is only Captain and owns every user discussion and confirmation; it starts Main from immutable launch input and never runs this phase itself. Visible Kimiflow Main owns Phase 1, may use its own ordinary FirstMate Scouts for bounded `stage=research` evidence, and routes one concise `needs-decision` artifact through FirstMate status to Captain. Captain discusses it and replies through `kimiflow_crew send`. Ships and confirmed review Scouts remain closed until the final contract and self-contained brief exist. A confirmed child does not create another Active Run, replay Phase 1, manufacture intake receipts, or talk to the user. Missing Main/Crew support is an explicit fallback, never a simulated hierarchy.
- **Intent Critic:** before planning, `large`/critical features run exactly one independent fresh-context critic over the request + compact provisional contract (≤900 input words, output only `COVERAGE_OK` or ≤5 missing user-owned facts; no HOW). Ask only for a genuinely absent material fact; otherwise proceed. Small runs may fold the same check locally. The critic never creates a confirmation checkpoint.

- **Feature → intent clarification:** perform the provenance scan, ask only for missing material facts, write the provisional `INTENT.md`, and continue to current-state research and planning. A build still needs current implementation authority; `plan`/`grill` stays no-code and never asks for future build permission.
- **Fix → working problem brief:** capture symptom, expected vs. actual, and available reproduction context in `PROBLEM.md`; inspect and diagnose immediately when sufficient. No routine Human Gate here. After the cause is proven, only a material product/authority/risk decision may pause before the bounded fix.
- **Audit → scope clarification:** capture paths, aggression, behavior-preserve constraints, do-NOT-touch hints, and what stays untouched → write `AUDIT-INTENT.md`. Discovery stays read-only and requests no cleanup authority; only a later user-selected fix slice may authorize implementation.
- **Mechanical clarify gate:** do not call it in Phase 1 for a fresh feature. Phase 4 records the one final schema-1 receipt, updates `INTENT.md` to the confirmed flow, then runs `clarify-gate.sh ... --record-intent-lock`. Existing schema-2 runs retain both legacy receipts and their current basis/research checks.
- **Mechanical adaptive classification (schema 5, non-trivial):** after confirmed Intent/Problem, rerun `hooks/adaptive-control.sh classify --run .kimiflow/<slug> --write`. If `product_decision_open=true`, return to this same intake boundary; never synthesize its answer. If its scope is higher than the active scope, run `hooks/active-run.sh rescope --run .kimiflow/<slug> --classification .kimiflow/<slug>/ADAPTIVE-CLASSIFICATION.json --write`; downgrade is forbidden. Copy only the receipt's exact `Domain complexity: off|active` and `Operational impact: off|active` selectors into STATE. The classifier is local, bounded, deterministic and adds no user gate.
